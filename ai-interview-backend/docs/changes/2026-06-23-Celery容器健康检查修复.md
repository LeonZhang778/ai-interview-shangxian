# Celery 容器健康检查修复

## 1. 功能说明

本次修复解决生产环境中 `ai-interview-celery-worker` 和 `ai-interview-celery-beat` 容器显示 `unhealthy` 的问题。

实际排查发现 Celery 进程本身在正常工作，worker 能收到并执行 beat 派发的定时任务；异常来自两个 Celery 容器继承了 app 镜像内的 HTTP healthcheck，错误地检查本容器的 `localhost:8006/api/v1/config/health`。Celery 容器不启动 HTTP 服务，因此 Docker 将其标记为 unhealthy。

修复后，worker 使用 Celery 自身的 `inspect ping` 做健康检查，beat 使用 `celerybeat-schedule` 调度文件存在性作为轻量健康信号，避免再用 app 的 HTTP 检查误判。

## 3. 核心实现逻辑

部署镜像中定义了 app 的 HTTP healthcheck，适合 `app` 容器，但不适合通过 `command` 覆盖启动命令的 Celery 容器。Compose 会继承镜像 healthcheck，除非服务级别显式覆盖。

本次在 `docker-compose.yml` 的 `celery-worker` 和 `celery-beat` 服务上添加服务级 healthcheck，覆盖镜像默认检查。

worker 通过 Celery 控制命令确认当前 worker 节点可响应：

```yaml
healthcheck:
  test: celery -A app.core.celery_app inspect ping --timeout=5 | grep -q "pong"
  interval: 30s
  timeout: 10s
  retries: 3
  start_period: 40s
```

beat 没有内建 HTTP 或 ping 接口，使用调度文件存在性确认进程完成启动并初始化调度状态：

```yaml
healthcheck:
  test: python -c "import pathlib; pathlib.Path('celerybeat-schedule').stat()"
  interval: 30s
  timeout: 10s
  retries: 3
  start_period: 40s
```

## 6. 验证记录

本地静态验证：

```bash
docker compose -f ai-interview-backend/docker-compose.yml config --quiet
```

结果：通过。

Compose 渲染检查确认：

- `celery-worker` healthcheck 渲染为 `CMD-SHELL celery -A app.core.celery_app inspect ping --timeout=5 | grep -q "pong"`
- `celery-beat` healthcheck 渲染为 `CMD-SHELL python -c "import pathlib; pathlib.Path('celerybeat-schedule').stat()"`

部署后需要在服务器执行最终验证：

```bash
cd /home/deploy/ai-interview/ai-interview-backend
docker compose ps
docker inspect ai-interview-celery-worker --format '{{.State.Health.Status}}'
docker inspect ai-interview-celery-beat --format '{{.State.Health.Status}}'
docker exec ai-interview-celery-worker celery -A app.core.celery_app inspect ping --timeout=8
docker logs ai-interview-celery-worker --tail 50
docker logs ai-interview-celery-beat --tail 50
```

预期结果：

- `ai-interview-celery-worker` 显示 `healthy`
- `ai-interview-celery-beat` 显示 `healthy`
- worker ping 返回 `pong`
- beat 持续派发定时任务，worker 正常消费任务
